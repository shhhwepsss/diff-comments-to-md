# local-review: два режима — GitHub PR и локальная папка

Дата: 2026-09-05
Статус: согласовано, к реализации

## Задача

Расширить тулу `local-review` до двух режимов работы, каждый — своя страница
одного и того же локального сервера и одного и того же UI.

1. **GitHub PR.** Работает только через GitHub, локального клона репозитория не
   требует вообще. Пользователь ищет PR-ы по репозиторию и поисковой строке,
   открывает PR, видит дифф, комментирует строки, экспортирует `.md`.
2. **Локальная папка.** Нынешнее поведение тулы, но без необходимости запускать
   её из нужного каталога: папка проекта выбирается прямо в UI.

Комментирование, редактирование, удаление, экспорт в `.md` и в буфер работают
на обеих страницах одним и тем же кодом.

## Что остаётся за рамками

- Отправка комментариев обратно в GitHub. По отношению к GitHub тула read-only.
- Показ существующих комментариев ревьюеров из PR-а.
- Клонирование репозиториев и любые git-операции на запись.
- Любые npm-зависимости, бандлеры, фреймворки.
- Аутентификация помимо `gh`.

## Зафиксированные решения

- Весь доступ к GitHub — только вызовом подпроцесса `gh`. Прямых HTTP-запросов к
  `api.github.com` и работы с токеном в коде тулы нет.
- Комментарии к PR-у хранятся вне репозитория, в домашнем конфиг-каталоге,
  отдельным файлом на каждый PR, ключ — хост + владелец + репозиторий + номер.
- Комментарии локального режима остаются в `.local-review/comments.json`
  в корне выбранного репозитория.
- Список недавно открытых репозиториев — в домашнем конфиге.
- Обзор каталогов — серверный эндпоинт, отдающий только имена подкаталогов и
  признак «это git-репозиторий». Содержимое файлов не читается никогда.
- Экспорт `.md`: в локальном режиме — в корень репозитория, как сейчас;
  в режиме PR — в домашний конфиг-каталог, путь показывается в UI.

## 1. Архитектура

### 1.1 Дескриптор источника

Всё, что определяет «на что мы сейчас смотрим», описывается дескриптором и
едет в каждом HTTP-запросе. Сервер не хранит «текущий выбор» как изменяемое
глобальное состояние: одно такое поле сломало бы две вкладки (одна на локальном
репозитории, другая на PR-е) и смешало бы счётчики комментариев.

```
local : { source: 'local', root: '<абсолютный путь к корню репозитория>' }
pr    : { source: 'pr', host: 'github.com', owner: 'o', repo: 'r', number: 25 }
```

В запросах — плоскими query-параметрами:

```
?source=local&root=C%3A%5CUsers%5C...%5Cproject
?source=pr&host=github.com&owner=o&repo=r&number=25
```

Это ровно тот приём, которым сегодня передаются `mode` и `base`
(`review.js:227-228`, `review.js:261-262`): читаются из запроса, дефолт берётся
из CLI-флагов, обратно в состояние сервера ничего не пишется.

Локальный дескриптор дополняется `mode` (`working` | `staged` | `base`) и
`base`, как сейчас. У PR-дескриптора режимов нет: сравнение всегда
head против base PR-а.

### 1.2 Интерфейс источника диффа

Две реализации за одним интерфейсом, выбор — фабрикой по дескриптору.

```js
// lib/sources/*.js
{
  id,                                  // ключ стораджа, см. 3
  async listFiles()                    // -> { files, range }
  async fileDiff(filePath, context)    // -> { ...entry, hunks, binary, additions, deletions }
}
```

`files[]` — единый формат для обоих источников:

```js
{ path, oldPath, status, kind, untracked?, additions?, deletions? }
```

**Нормализация — в адаптере, не в UI.** GitHub отдаёт словесные статусы
(`added` / `modified` / `removed` / `renamed` / `copied`), а UI и CSS уже умеют
однобуквенный алфавит `A/M/D/R/C` (`public/app.js:106`,
`public/styles.css:216-223`). Адаптер PR-а приводит статусы к этому алфавиту,
фронт не узнаёт о существовании второго словаря.

Признаки, специфичные для одного источника:

- `untracked` ставит только локальный источник (`lib/diff.js:68`).

Отсутствующий признак — `undefined`, что фронт уже переносит нормально
(`review.js:246`).

### 1.3 Локальный источник

`lib/sources/local-source.js` — тонкая обёртка над нынешними
`listFiles(repoRoot, mode, base)` (`lib/diff.js:71`) и
`fileDiff(repoRoot, mode, base, file, context)` (`lib/diff.js:200`).
Логика диффа не меняется вообще.

### 1.4 PR-источник

`lib/sources/pr-source.js`.

**Один запрос на весь дифф.** `gh pr diff <number> --repo <owner>/<repo>` отдаёт
дифф всего PR-а в обычном git-формате. Из него достаётся и список файлов, и
содержимое каждого диффа — второй источник данных не нужен.

Ответ режется по границам `diff --git a/… b/…` на блоки, по одному на файл.
Из шапки блока читается статус, из тела — хунки:

| Строка в шапке | Что означает | `status` / `kind` |
| --- | --- | --- |
| `new file mode …` | файл добавлен | `A` |
| `deleted file mode …` | файл удалён | `D` |
| `rename from` / `rename to` | переименование | `R` |
| ничего из перечисленного | изменён | `M` |
| `Binary files … differ` / `GIT binary patch` | бинарный | `binary: true` |

Тело блока скармливается **существующему** `parsePatch` (`lib/diff.js:102`) без
изменений: он корректно обрабатывает фрагмент одного файла, уже выдаёт реальные
номера строк old/new и уже распознаёт бинарные маркеры (`lib/diff.js:113`).
Это главная точка переиспользования — номера строк в PR-режиме считает ровно тот
же код, что и в локальном. `additions` / `deletions` считаются из разобранных
хунков, отдельный источник счётчиков не нужен.

Проверено вживую на `gh 2.96.0`: вывод начинается с `diff --git`, содержит
`new file mode`, `index`, хунки — стандартный git-формат.

Метаданные PR-а (заголовок, ветки, автор, состояние) — отдельный вызов
`gh pr view <number> --repo o/r --json …`. Это шапка экрана, а не дифф; он же
добирает имя ветки, когда поиск шёл без указания репозитория.

**Если дифф не отдался.** У очень больших PR-ов GitHub может отказать. Никаких
запасных дорог на этом этапе не строим: показывается читаемое сообщение
(«GitHub не отдал дифф этого PR-а») и ссылка на PR. Если в жизни окажется, что
это мешает, решаем тогда, с фактом на руках.

### 1.5 Поиск PR-ов

`lib/pr-search.js`, отдельно от `pr-source.js`: «искать PR» (дескриптора ещё
нет) и «читать дифф выбранного PR-а» (дескриптор уже есть) — разные стадии.

Поле «репозиторий» **опциональное**:

| Репозиторий | Автор | Команда | Ветка в выдаче |
| --- | --- | --- | --- |
| задан | все | `gh pr list --repo o/r --search <q> --state <s> --json number,title,author,headRefName,baseRefName,updatedAt,url,state,isDraft` | есть |
| задан | мои | то же плюс `--author @me` | есть |
| пусто | мои | `gh search prs --author=@me --state=<s> --json number,title,repository,author,state,updatedAt,url,isDraft` + строка запроса | нет, показывается `—` |
| пусто | все | то же, но `--involves=@me` вместо `--author=@me` | нет, показывается `—` |

Фильтр по автору добавлен позже первой версии (#19). «Все» без репозитория —
это `--involves=@me`: PR, где пользователь автор, исполнитель, упомянут или
запрошен как ревьюер. Показать вообще все PR на GitHub нельзя и незачем,
поэтому «все» здесь означает «все, где я участвую». Фильтр всегда уходит
флагом `gh`, строка запроса пользователя не трогается.

Причина расхождения: у `gh search prs` в списке полей `--json` нет
`headRefName` (проверено на `gh 2.96.0`). Ветка в этом случае подтягивается
при открытии PR-а, не N+1 запросом на весь список.

Фильтр состояния: `open` | `closed` | `merged` | все. У `gh search prs` состояние
`merged` выражается через `--merged`, у `gh pr list` — через `--state merged`;
разница прячется внутри `pr-search.js`.

### 1.6 Обёртка над `gh`

`lib/gh.js` — единственное место в коде, где вызывается `gh`. По образцу
`lib/git.js`: `spawn` с массивом аргументов, `shell: false`, никакого
интерполирования строк. Бинарь берётся как
`process.env.LOCAL_REVIEW_GH_BIN || 'gh'` — это же даёт точку подмены для
smoke-теста (см. 6).

Классификация ошибок в читаемые сообщения, а не stack trace:

| Признак | Сообщение в UI |
| --- | --- |
| `spawn` → `ENOENT` | «`gh` не установлен. Установи GitHub CLI и выполни `gh auth login`.» |
| ненулевой код + `auth`/`not logged` в stderr | «Ты не залогинен в `gh`. Выполни `gh auth login`.» |
| stderr содержит `rate limit` | «Превышен лимит GitHub API. Подожди и повтори.» |
| stderr содержит `dial tcp` / `no such host` / `timeout` | «Нет связи с GitHub.» |
| HTTP 404 | «Репозиторий или PR не найден, либо нет доступа.» |
| прочее | текст stderr, обрезанный до первой строки |

## 2. HTTP-слой

### 2.1 Новые эндпоинты

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/gh/status` | `{installed, authenticated, login, host, message}` |
| GET | `/api/pr/search?repo=&q=&state=&limit=` | список PR-ов |
| GET | `/api/pr/resolve?...` | метаданные PR-а: заголовок, ветки, headSha, автор |
| GET | `/api/browse?path=` | `{path, parent, separator, entries:[{name, isRepo}]}` |
| GET | `/api/local/validate?root=` | `{ok, repoRoot, sameAsRequested, error}` |
| GET | `/api/session` | последний дескриптор + список недавних репозиториев |
| POST | `/api/session` | сохранить последний дескриптор / добавить недавний репозиторий |

### 2.2 Существующие эндпоинты

Форма ответов не меняется, добавляется приём дескриптора:

`/api/state`, `/api/diff`, `/api/comments` (GET, POST),
`/api/comments/:id` (PUT, DELETE), `/api/comments/clear-all`,
`/api/export/text`, `/api/export/file`.

Дескриптор передаётся в query-строке во всех методах, включая POST и DELETE —
единообразно, чтобы не было двух мест, откуда он читается.

### 2.3 Обзор каталогов

`lib/browse.js`. Отдаёт только имена подкаталогов и флаг `isRepo`
(наличие `.git` непосредственно внутри). Содержимое файлов не читается никогда,
файлы в выдачу не попадают.

Подъём вверх — только когда клиент сам прислал путь родителя (кнопка «..»).
Сервер сам никуда не поднимается и никакого корня по умолчанию не сканирует.
Поле `parent` — подсказка для этой кнопки, не автоматическое действие.

Без параметра `path` отдаётся стартовый набор: домашний каталог пользователя и
недавние репозитории.

### 2.4 Выбор папки и подъём к корню

Для любого пути `P` — хоть из UI, хоть из `--cwd`, хоть из текущей папки при
запуске:

| Что нашли | Что происходит |
| --- | --- |
| `git rev-parse --show-toplevel` не сработал | ошибка «`P` — не git-репозиторий», пользователь остаётся на экране выбора |
| корень `R` совпал с `P` | открывается сразу, молча |
| корень `R` выше `P` | модалка «Выбран `P`. Это подкаталог репозитория `R`. Дифф будем читать из корня `R`. Открыть?» → [Отмена] / [Открыть корень] |

Отмена ничего не открывает. Модалка — существующий оверлей
(`public/index.html:49-58`), не нативный `confirm()`: нативные диалоги блокируют
браузерную автоматизацию, которой проверяется живой прогон.

Следствие для сервера: при запуске из подкаталога он не «решает» корень молча,
а отдаёт фронту кандидата и признак `sameAsRequested: false`; открытие
происходит после подтверждения. Если в адресной строке уже стоит явный `root=`
(возврат по ссылке или после перезапуска), спрашивать нечего.

### 2.5 Проверка происхождения запроса

Сервер отклоняет кросс-сайтовые запросы по заголовкам `Origin` /
`Sec-Fetch-Site`. Причина: выбор папки из UI превращает фиксированный при старте
путь в значение, которое присылает клиент, — сервер начинает по запросу из
вкладки перечислять каталоги и писать `.local-review/comments.json` в указанную
папку. Слушаем по-прежнему только `127.0.0.1` (`review.js:30`), проверка
заголовков — дешёвая вторая линия.

## 3. Хранилище

### 3.1 Разделение ответственности

`CommentStore` сейчас сам вычисляет путь из `repoRoot` (`lib/store.js:13-14`) —
то есть держит в себе знание о раскладке локального режима. Меняется на приём
**абсолютного пути к файлу**: `CommentStore` становится тупым JSON-стораджем и
не знает, что режимов два. Методы `load/save/all/countsByFile/add/update/remove/
clearAll` (`lib/store.js:19-105`) не меняются.

Единственное место, где дескриптор превращается в путь, — `lib/stores/factory.js`:

```
local : <root>/.local-review/comments.json
pr    : <homeConfig>/pr/<host>__<owner>__<repo>__<number>.json
```

Так инвариант «стораджи не пересекаются» проверяется одной функцией, а не
доверием к каждому месту вызова.

### 3.2 Домашний конфиг

```
~/.local-review/
  state.json                    последний дескриптор + недавние репозитории
  pr/<host>__<owner>__<repo>__<number>.json
  exports/review-<YYYY-MM-DD-HHmm>.md
```

Имя PR-файла санируется: всё, кроме `[A-Za-z0-9._-]`, заменяется на `_`.

Автоочистки нет — принято сознательно. На экране поиска PR-ов показывается путь
конфига и число хранимых PR-ов, чтобы каталог не рос незаметно.

### 3.3 Экспорт

`renderMarkdown` и `anchorOf` (`lib/export.js:12-36`) уже не зависят от
источника — смотрят только на `file`, `startLine`, `endLine`, `text`. Меняется
только каталог назначения у `writeMarkdownFile`: корень репозитория в локальном
режиме, `~/.local-review/exports/` в режиме PR. Путь показывается в UI после
записи, как сейчас.

## 4. Фронт

### 4.1 Роутинг

Хеш-роутер, одна страница, три экрана:

| Хеш | Экран |
| --- | --- |
| `#/local` | выбор папки; после выбора — `#/local/<путь>` |
| `#/pr` | поиск PR-ов |
| `#/pr/<host>/<owner>/<repo>/<number>` | дифф PR-а |

Хеш — источник правды о текущем контексте. «Выбор переживает перезапуск сервера»
обеспечивается `~/.local-review/state.json`: последний дескриптор читается
**только** когда хеш пуст. `localStorage` тут не годится — при перезапуске порт
может смениться, а это другой origin.

### 4.2 Разбиение файлов

`public/app.js` сегодня — 786 строк, в которых шапка экрана
(`public/app.js:75-90`) перемешана с логикой диффа и комментариев при одном
глобальном `state` (`public/app.js:23-33`). Навешивать роутер на это как есть —
значит продолжить растить тот же файл. Порядок работ: сначала выделение, потом
роутер.

| Файл | Содержимое |
| --- | --- |
| `public/api.js` | `api()`, `toast()` |
| `public/diff-view.js` | рендер диффа, карточки комментариев, редактор, протяжка по номерам строк, экспорт — общий код обеих страниц |
| `public/screen-local.js` | выбор папки, недавние, модалка подъёма к корню, переключатель `working/staged/base` |
| `public/screen-pr.js` | статус `gh`, форма поиска, список результатов, шапка PR-а |
| `public/app.js` | роутер, общая шапка, переключение экранов |

Подключение — обычными `<script>`-тегами по порядку, глобальные функции.
Никаких модулей-сборщиков: ноль зависимостей остаётся инвариантом.

### 4.3 Модули сервера

| Файл | Содержимое |
| --- | --- |
| `lib/gh.js` | подпроцесс `gh`, классификация ошибок |
| `lib/pr-search.js` | поиск PR-ов |
| `lib/sources/local-source.js` | локальный источник |
| `lib/sources/pr-source.js` | PR-источник: разбор `gh pr diff` на файлы |
| `lib/sources/factory.js` | дескриптор → источник |
| `lib/stores/factory.js` | дескриптор → путь к файлу комментариев |
| `lib/browse.js` | обзор каталогов, валидация корня |
| `lib/config.js` | домашний конфиг: пути, `state.json`, недавние |
| `lib/routes/*.js` | нынешние inline-блоки (`review.js:226-353`) как функции `(req, res, ctx)` |

`review.js` возвращается к процессным заботам: разбор флагов, статика,
`listen` с перебором портов, открытие браузера, `.gitignore`
(`review.js:112-134`, `review.js:359-389`) — порядка 200 строк.

## 5. Инварианты

Проверяются и автотестом, и живым прогоном.

1. Экспорт (в файл и в буфер) не изменяет и не удаляет комментарии.
2. Массовое удаление — только с `{"confirm": true}` в теле запроса, а в UI —
   только после подтверждения в модалке; отмена, `Esc` и клик по фону не удаляют
   ничего.
3. Комментарии переживают перезапуск сервера и перезагрузку страницы в обоих
   режимах.
4. Номера строк в экспорте — реальные номера строк в файле после изменений, а не
   позиции внутри диффа. Одинаково для локального диффа и для диффа из GitHub.
5. Стораджи не пересекаются: комментарии к PR-у никогда не попадают в файл
   локального репозитория, комментарии локального режима — в PR-сторадж.
6. Тула не выполняет git-команд на запись и не пишет в исходники проекта.
   Единственное исключение — строка `.local-review/` в `.gitignore` репозитория;
   см. раздел 7, пункт 7.
7. Ноль npm-зависимостей: список зависимостей в `package.json` пуст.
8. Эндпоинт обзора каталогов не отдаёт содержимое файлов и не выходит вверх без
   явного запроса пользователя.
9. Отсутствие `gh`, отсутствие логина, ошибка сети и превышение лимита GitHub API
   дают читаемое сообщение в UI, а не пустой экран и не stack trace.

## 6. Проверка

### 6.1 Автотест

`tools/local-review/smoke.js` расширяется. GitHub-сценарий работает на
фикстурах: `lib/gh.js` спавнит `process.env.LOCAL_REVIEW_GH_BIN || 'gh'`, тест
подставляет свой скрипт, отвечающий заранее записанными ответами по argv.
Реальная сеть в автотесте не используется, прод-код при этом остаётся честным
подпроцессом.

Фикстуры покрывают: PR без изменённых файлов; PR с бинарным файлом; PR с
переименованием; PR, дифф которого GitHub отдать отказался;
пустой результат поиска; репозиторий без доступа (404); отсутствие `gh`
(`ENOENT`); отсутствие логина; превышение лимита; сетевую ошибку; кириллицу и
пробелы в путях и именах файлов; CRLF.

Каждый инвариант из раздела 5 получает проверку с ненулевым кодом выхода при
расхождении.

### 6.2 Живой прогон в браузере

Настоящий сервер, настоящий `gh`, настоящие PR-ы, настоящий репозиторий с
незакоммиченными изменениями. Кликами в UI, а не запросами к эндпоинтам:

- оба сценария приёмки целиком;
- комментарий к строке, к диапазону протяжкой, к файлу целиком; редактирование
  и удаление одного комментария;
- экспорт `.md` и в буфер, после каждого — проверка, что комментарии на месте;
- модалка массового удаления: отмена, `Esc`, клик по фону ничего не удаляют;
- перезагрузка страницы и перезапуск сервера в обоих режимах;
- переключение между страницами с непустыми комментариями в каждой: списки и
  счётчики не смешиваются;
- экран ошибки при недоступном `gh` и при выборе не-git-каталога.

Консоль браузера и сетевые запросы читаются по ходу: ни одной необработанной
ошибки, ни одного ответа 5xx. Скриншоты: список PR-ов, дифф PR-а с
комментарием, экран выбора локальной папки, дифф локального репозитория, экран
ошибки при недоступном `gh`.

## 7. Принятые ограничения

Вынесены пользователю явно и подтверждены.

1. **`~/.local-review/` растёт вечно.** Ни `.gitignore`, ни автоочистки. Путь и
   число хранимых PR-ов показываются на экране поиска.
2. **`gh` становится обязательной зависимостью PR-режима.** README сейчас
   утверждает, что тула «никогда не ходит в сеть» (`README.md:86-87`) — это
   станет неправдой, формулировка меняется на «локальный режим — только чтение
   git; PR-режим ходит в сеть исключительно через `gh` и ничего не отправляет в
   GitHub на запись».
3. **Расширение доверенной границы.** Путь к репозиторию перестаёт быть
   фиксированным при старте и начинает приходить от клиента. Смягчено проверкой
   `Origin`/`Sec-Fetch-Site` и привязкой к `127.0.0.1`.
4. **Ветка в результатах поиска без указания репозитория не показывается** —
   `gh search prs` её не отдаёт. Подтягивается при открытии PR-а.
5. **Для PR-а, дифф которого GitHub отдать отказался, запасной дороги нет** —
   показывается читаемое сообщение и ссылка на PR. Скачивание файлов по
   отдельности сознательно не делаем: если проблема встретится в жизни, решаем
   её тогда, с фактом на руках.
6. **`CommentStore` меняет сигнатуру конструктора** с `(repoRoot)` на
   `(filePath)`. Это правка протестированного модуля; smoke гоняет сервер через
   `start()` (`smoke.js:21`), а не `CommentStore` напрямую, поэтому должен
   пережить — но проверяется прогоном, а не предположением.
7. **Запись в `.gitignore` выбранного репозитория.** Тула уже сегодня дописывает
   строку `.local-review/` в `.gitignore` того репозитория, который открывает
   (`review.js:112-134`), и нынешний smoke это проверяет. Раньше репозиторий был
   один и выбирался при запуске процесса; теперь его выбирает пользователь в UI,
   значит эта запись будет происходить в каждый открытый им проект. Решение —
   поведение сохраняем, но запись выполняется **только после** подтверждения
   выбора папки, никогда при простом обзоре каталогов, и факт записи
   показывается в UI строкой «в `.gitignore` добавлено `.local-review/`».
